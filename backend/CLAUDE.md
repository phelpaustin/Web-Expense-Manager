# Backend (FastAPI + SQLAlchemy)

Loaded when working under `backend/`. Commands and cross-cutting rules are in the root `CLAUDE.md`.

## Map
- `backend/main.py` – app setup, CORS, router registration; runs Alembic migrations + seed on startup.
- `backend/app/api/` – one router per area (auth, expenses, bills, groups, trips, budgets, income, recurring, options, alerts, aliases, analytics, metrics). Thin: validation, permissions, DB access.
- `backend/app/api/dashboard.py` – ONE endpoint that returns everything the dashboard shows (summary, trends, categories, budgets, metrics, period status, alerts), loading and converting expenses once. Reuse its helpers (`summary_payload`, `trends_payload`) instead of adding another endpoint that re-scans all expenses.
- `backend/app/api/bill_sync.py` – keeps every expense represented in Spending, By receipt by "adopting" unlinked expenses into derived bills (`origin='expenses'`) and reconciling them when items change. Idempotent; unique index (user, origin_key) makes races safe. GET endpoints never write: writes call `adopt_after_write`, startup runs `backfill_all`, and `GET /bills` returns `needs_sync` so the page calls `POST /bills/sync` once.
- `backend/app/api/statement_import.py` + `logic/statement_import.py` + `core/ai_import.py` – bank statement import: `/import/analyze` (find table, guess `Mapping`), `/import/preview` and `/import/commit` (the same `classify()` call, so preview == save), `/import/assist` (LLM turns a typed instruction into a validated `Mapping`; only headers + ~10 sample rows leave the server), `/import/profiles` (saved mappings found by `header_signature`). Stateless: every call carries the file. Frontend: `pages/ImportPage.jsx` (tabs: Bank statement, and `components/ExpenseFileImport.jsx` for files in the app's own expense format, `/expenses/import`) + `statementImport.js`. Importing lives only on the Import page (a statement can be saved as expenses or, with `save_as=bills`, as bills to itemise later); Export is in Settings. The older `/pending-bills/bulk-upload` endpoint has no screen any more and is kept only until the bills clean-up.
- `backend/app/api/deps.py` – `get_current_user` (JWT + session_version + email_verified) and group role helpers (owner > admin > editor > viewer).
- `backend/app/logic/` – pure functions on plain dicts (no DB, no FastAPI): analytics, category change ("what changed"), period compare (a month against last month, last year and the 3-month average; `GET /api/analytics/compare`), movers (categories and shops that rose, fell or are new; `GET /api/analytics/movers`, shop names follow the user's merges), recurring costs (cost per month/year of each recurring template, next due, price rises from the payments it posted, compared in the template's own currency; `GET /api/analytics/recurring-costs`), unusual (`unusual_expenses`: a recent expense at least 3× its category median and above the upper Tukey fence, using 12 months of the other expenses; `possible_duplicates`: same day, amount, description and shop, where lines of one *real receipt* count once — derived bills (`origin='expenses'`) only group hand-typed entries, so the caller passes `receipt_bills`; `GET /api/analytics/unusual`; nothing is stored, so there is no "not a duplicate" dismissal), patterns (`spending_patterns`: average per calendar day for each weekday and each part of the month — days 1–7, 8–14, 15–21, 22–31 — over the last N months, so a window with five Saturdays doesn't favour Saturday; recurring payments are left out because they land on their due date; `enough` is false below 20 expenses / 28 days and then no busiest/quietest is named; `GET /api/analytics/patterns`), report (`build_report`: the yearly or monthly report — totals, income/net/savings rate, change from the previous year/month, categories, spending by month or by day with its peak, a category-by-month table for a year, top shops, largest expenses; every expense counts, refunds included, so the total equals the dashboard's; `GET /api/reports` in `api/reports.py`, shop merges applied; income is the user's own whatever the scope), forecast (tested methods, range, categories), budget risk (chance of exceeding a budget), spending mix (committed/everyday/one-off), shop scorecard, budgets, alerts, price tracker (also `cheapest_shops`: the same item, unit, category and brand compared across shops over a recent window; `GET /api/analytics/price-trends/cheapest-shops`), price rises (`price_rises`: the same product at the same shop, newest purchase against the earlier average; `GET /api/analytics/price-trends/rises`; the biggest also become bell alerts via `alerts.price_rise_alerts`, and the daily digest email stays budget-only; `rows_for_price_rises` trims history before renaming so the dashboard stays fast), units, categorizer, names/aliases, taxonomy, search, trips/settlement, currency conversion. Put business rules here and test them directly.
- `backend/app/core/report_files.py` – the report as an Excel workbook (openpyxl, native charts, free text neutralised with `escape_formula`) and a PDF (`reportlab`, pinned in requirements; built-in Helvetica, so characters outside Windows-1252 print as `?`); both only lay out the dict from `logic/report.py`, so files and screen agree. `GET /api/reports/export?format=xlsx|pdf&year=&month=`. Frontend: the Report tab on `pages/InsightsPage.jsx` (`components/ReportPanel.jsx` + `report.js`).
- `backend/app/core/` – config, security (JWT/bcrypt), email (Resend/SMTP), `fx.py` (Frankfurter rates, cached), money/parsing/upload helpers, rate limiting, `receipt_storage.py` (receipt files: Supabase Storage when configured, else the `receipts.data` column; reads follow the row's `storage_key`; `python -m app.scripts.migrate_receipts --sweep` finds orphaned objects).
- `backend/app/db/` – `models.py`, session, seed, one-off data repairs (`category_cleanup`, `bill_shop_cleanup`, `recurring_link_cleanup`). Schema changes go through `backend/alembic/versions/` (next number: 0029). `manual_bills` (the old manual ledger) is no longer a model; migration 0028 drops the table only when it is empty and otherwise keeps it with a printed warning, and `delete_account` clears any leftover rows. Revision ids must be at most 32 characters (`alembic_version.version_num` is VARCHAR(32)); `tests/test_migration_ids.py` guards it.
- `backend/tests/` – pytest; `conftest.py` provides `client`, `make_user`, fake FX.

## Conventions
- Money is `Decimal` / `Numeric(12,2)`; never use floats for amounts. Every record carries its own `currency`; totals are converted to the user's reporting currency at each row's date.
- The forecast (`logic/forecast.py`) is pure Python with no statsmodels/scipy; it forecasts baseline spending (not one-offs) and chooses its method by backtesting on the user's own months. Don't add a second forecast number elsewhere in the UI.
- Tests run on SQLite but production is Postgres. SQLite ignores column widths and is lax about types, so anything width- or type-sensitive (migration ids, new columns, raw SQL) can pass every test and still fail the deploy.
- An expense posted by a recurring template carries `recurring_template_id` (no foreign key, so cancelling a template keeps its past payments committed). "Committed" means that field is set; clients can't set it. One-offs are computed on read (`logic/spending_mix.py`), never stored.
- Every section of the `/dashboard` payload must equal its standalone endpoint (`tests/test_dashboard_endpoint.py`), so a new section needs its own endpoint (e.g. `budget_risk` is also `GET /api/budgets/risk`). Budget risk (`logic/budget_risk.py`) takes the budget bars' own statuses as input, and `generate_alerts(..., risk)` falls back to the old straight-line rule only when there is too little history.
- Emails are lowercased (`app/core/emails.py`); categories are case-insensitive via `logic/taxonomy.py`.
- A bill recorded as a single total is an expense with `bill_total_only=True`: its `shop` is the bill's shop and its `description` is the same name, so it is a shop trip, not an item. Item/price analytics (price tracker, alias item suggestions) must skip these rows; shop spend counts them.
- Account existence is never revealed: register, resend-verification, forgot-password and group invites answer identically for known and unknown addresses (emails go out as background tasks). Invitations are accepted by the invitee (`/groups/invitations`), never applied automatically to an existing account.
- Tests accompany behaviour changes: backend in `backend/tests/`, frontend in `frontend/src/__tests__/`.
